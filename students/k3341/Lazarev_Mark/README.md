# Лабораторные работы 1–3

Лазарев Марк, ИСУ 368418, группа K3341

Проект «Time Manager» — приложение для управления задачами и учёта времени.
Три работы развивают одну систему: Lr1 — само приложение, Lr2 — эксперимент
с параллелизмом, Lr3 — упаковка в Docker и очередь задач.

## Состав

| Папка | Работа | Содержание |
|---|---|---|
| `Lr1` | Серверное приложение | FastAPI, PostgreSQL, SQLAlchemy 2.0, миграции Alembic, JWT |
| `Lr2` | Параллелизм | threading / multiprocessing / asyncio на CPU- и I/O-задачах |
| `Lr3` | Docker и очередь | docker compose, микросервис-парсер, Celery + Redis |

Отчёт по каждой работе — `docs/index.html` внутри соответствующей папки.

## Быстрый запуск

Нужен Docker и Docker Compose.

```bash
cd Lr3
cp .env.example .env     # заполнить своими значениями
docker compose up --build
```

Поднимутся шесть сервисов:

- `db` — PostgreSQL
- `redis` — брокер очереди
- `migrate` — разово применяет миграции Alembic и завершается
- `parser` — сервис парсинга, http://localhost:8001/docs
- `api` — приложение Lr1, http://localhost:8000/docs
- `celery_worker` — обработчик фоновых задач

Порядок старта задан healthcheck'ами: `api` и `celery_worker` поднимаются только
после того, как база готова, Redis отвечает и миграции успешно применились.

## Lr1 — приложение

Шесть таблиц: `users`, `categories`, `tags`, `tasks`, `task_tags`, `time_entries`.
Реализованы связи one-to-many (категория → задачи) и many-to-many с собственным
полем в связующей таблице (задача ↔ тег, поле `note`). 31 эндпоинт, все кроме
регистрации и входа защищены JWT.

`GET /tasks/{id}` возвращает задачу вместе с тегами и записями времени —
связи подтягиваются одним запросом через `joinedload`, чтобы избежать N+1.

Конфигурация задаётся переменными окружения. В `alembic.ini` параметр
`sqlalchemy.url` не используется — URL приходит из `DATABASE_URL` и
подставляется в `alembic/env.py`. Образцы настроек — в файлах `.env.example`.

Запуск без Docker — см. `Lr1/README.md`.

## Lr2 — параллелизм

`task1` — подсчёт суммы 1..10 000 000 четырьмя параллельными частями.
`task2` — парсинг 8 сайтов с записью заголовков в базу Lr1.
В каждой задаче три реализации и `benchmark.py`, который прогоняет их подряд
и печатает таблицу сравнения.

Вывод: на счёте выигрывают процессы, потоки упираются в GIL; на сети выигрывают
потоки и async, а процессы проигрывают на накладных расходах запуска.

Скрипты запускаются на хосте, не в контейнере — для `task2` нужна поднятая база
(`cd ../Lr3 && docker compose up -d db`) и заполненный `Lr1/.env`.

## Lr3 — микросервисы и очередь

Логика парсинга из Lr2 вынесена в отдельный сервис со своим Dockerfile и
своими зависимостями — он не импортирует код Lr1 и общается с ним по HTTP.

Парсер вызывается двумя способами:

- `POST /parser/parse` — синхронно, клиент ждёт результат
- `POST /parser/parse/async` — задача уходит в очередь Redis, клиент сразу
  получает `task_id`, работу выполняет Celery-воркер в фоне
- `GET /parser/task/{task_id}` — статус и результат задачи

При недоступности парсера синхронный вызов отдаёт 503, не роняя API,
а задача из очереди повторяется до трёх раз.
